# ProcessLens 交付可行性分析（资深项目经理视角）

> 分析对象：`docs/ProcessLens_需求文档.md`（Draft v1.0，主依据）、`docs/ProcessLens_单App行为监控器_项目企划书.txt`（上游企划）
> 分析日期：2026-09-24
> 视角：交付可行性 —— Gate 可判定性、关键路径、需求-阶段映射、范围与决策机制

## 总体结论

**结论：有条件可交付，但需求稿在"可判定性"和"项目管理要素"两个维度上存在系统性缺口，当前版本不足以直接驱动排期与验收。**

具体判断：

1. **需求质量本身较好**。FR/NFR 编号完整、优先级清晰、Scope Exclusion（§8）与产品边界（§1.3）写得克制且一致，"只陈述观察事实"的原则在 FR-3.3、FR-4.3、FR-5.9、NFR-2.3 中形成了闭环——这是这份文档最强的部分。

2. **最大的结构性问题：Go/No-Go 机制名义存在、实际不可执行**。企划书 §19 给出"Conditional Go"，需求稿 §1.4 重申 entitlement 是 Go/No-Go 条件，但两份文档都没有给出"多久算长期不获批"的时间阈值、No-Go 触发后的处置路径、以及"Windows beta 先行"在需求层面的落地条目。目前的风险表（§11）只有缓解措施，没有决策规则。

3. **G0 存在被低估的外部依赖**。G0 Gate 只写了"提交 Endpoint Security entitlement + 确认 Network Extension Developer ID 配置"（§10、NFR-3.1）。按 Apple 现行规则，Network Extension 的 content-filter-provider entitlement 同样需要向 Apple 申请审批，不是纯"配置确认"事项。如果属实，G0 实际是两个并行审批，关键路径比文档表述更长。

4. **Gate 验收语普遍缺度量**。五个 Gate 中仅 G2（"10–30 分钟 Session 稳定"，对应 NFR-1.3）接近可判定；G1"单 Session 数据可信"、G3"非安全专业用户可看懂"、G4"真实用户环境可持续使用"均无量化标准，届时无法客观判定通过与否。

5. **需求到阶段的映射是断的**。全部 P0/P1 条目中只有 5 条标注了阶段归属（NFR-3.1→G0、NFR-1.3→G2、NFR-4.1→G3、FR-2.4/FR-6.6→G4），其余约 30 条需求没有阶段锚点。这意味着无法回答"每个 Gate 交付哪些需求"，也无法做阶段级的范围控制。

6. **项目管理要素整体缺失**：无时间维度（全部里程碑无工期或日期）、无版本与更新策略、无变更管理流程、无 OS 版本兼容矩阵、无 Windows 代码签名依赖。对免费品牌项目而言，工期弹性可以接受，但 Go/No-Go 时间点和 Windows 签名这两项是硬缺口。

### 无阶段归属且阶段表外溢的条目

- **P1 条目悬空**：FR-2.5（Session 对比）、FR-4.4（DNS/flow 关联）、UC-5 均无阶段归属，G0–G4 中也无"1.x 版本"位置。建议显式标注"post-G4 / 1.x 候选"，避免 Beta 期间被误认为 P0 未完。
- **G0 的 NE 确认事项无强需求支撑**：NFR-3.1 后半句"Network Extension 使用对应 Developer ID entitlement 配置"是唯一对应条目，且措辞为配置而非审批（见 PM-R02）。
- **G4"真实用户环境可持续使用"无需求支撑面**：beta 规模、测试用户来源、反馈渠道、崩溃率阈值全无对应条目，Gate 实际无法验收（见 PM-R06）。
- **跨阶段横切需求未标识**：NFR-2.x（隐私边界）、FR-5.9（时序≠因果文案）属于从 G1 起就应遵守的全程约束，建议在文档中标识为"全阶段适用"。

## 建议新增/修改的条目

以下按"修改现有条目 / 新增条目"分组，编号为建议值。

### 修改现有条目

- **PM-M01｜§1.4 Go/No-Go**：补充可判定条件——"G0 提交后 T+90 天未获批 → 状态评审并决定是否全量转 Windows 先行；T+180 天未获批 → 正式 No-Go 评审，macOS 正式版中止，项目处置三选一（Windows-only 继续 / 暂停等待 / 归档），不退化为快照工具维持 §8 结论不变"。
- **PM-M02｜§10 G0 Gate**：改为"ES 与 NE content-filter 两项 entitlement 均已提交申请（或书面确认 NE 无需审批）；macOS PoC 在无 entitlement 条件下的技术路径已验证并记录结论"。
- **PM-M03｜§10 G1/G3/G4 Gate**：补度量（对应 PM-R06）：G1"对照基线工具事件覆盖率 ≥ 约定阈值且归属无误判案例"；G3"≥5 名目标用户独立完成核心问题作答"；G4"beta 用户 ≥N 名、连续使用 ≥2 周、崩溃率 ≤X%"。
- **PM-M04｜§10 阶段表**：增加"需求覆盖"列，落实上节映射表，每条 P0 需求有唯一主归属阶段。
- **PM-M05｜§11 风险表**：增加三行——NE entitlement 审批不确定性、Windows 代码签名/SmartScreen、需求变更无评审流程；外部依赖清单补 Windows 签名证书。
- **PM-M06｜文档头**：上游文档文件名改为 `docs/ProcessLens_单App行为监控器_项目企划书.txt`，并记录 AppScope→ProcessLens 更名。

### 新增条目（建议编号）

- **PM-N01｜FR-2.6（或 NFR-3.4）Windows 独立发布路径**：Windows 版可在 macOS entitlement 未决时独立进入 Beta/发布流程，功能集为 P0 中平台无关子集；明确"Windows beta 先行"是正式产品路径而非降级方案。
- **PM-N02｜NFR-3.x Windows 签名与分发**：Windows 安装包需 OV/EV 代码签名；采集服务安装需管理员权限并明确 UAC 流程。
- **PM-N03｜NFR-4.x / 新 NFR-5 OS 兼容矩阵**：macOS 最低支持版本（建议 ≥13，以系统扩展与 ES API 行为为准）、Windows 10/11；G4 测试矩阵按此界定。
- **PM-N04｜NFR-5 版本与更新策略**：版本号规则；更新分发方式（自动更新框架 vs 手动下载）决策点不晚于 G4；系统扩展/服务与 GUI 的版本协同升级约束。
- **PM-N05｜新增 §13 变更管理**：P0 范围在 G2 Gate 通过后冻结；P1→P0 升级需书面评审并更新本文档版本号；范围蔓延控制责任落到单人决策点（免费项目默认即作者本人，规则仍需明示）。
- **PM-N06｜决策项（非需求条目）**：开源范围（企划书 §14"至少开源采集器/系统扩展"）与品牌入口（About "Built by…"）两项上游决策需在 G3 前给出结论：纳入需求则补 FR，否则显式暂缓。
