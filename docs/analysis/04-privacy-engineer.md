# ProcessLens 隐私工程师视角分析

> 分析对象：`docs/ProcessLens_需求文档.md`（PRD Draft v1.0，主依据）
> 参照文档：`docs/ProcessLens_单App行为监控器_项目企划书.txt`（上游企划）
> 视角：Privacy Engineering —— 关注被采集元数据的完整生命周期（采集 → 存储 → 展示 → 导出 → 删除）是否有对应的技术控制，而非仅看"不采内容"的承诺。
> 日期：2026-09-24

---

## 总体结论

需求文档在**采集侧的最小化**做得比较到位：不采文件内容（FR-3.3）、不抓 payload（FR-4.3）、全本地、无账户、默认无遥测（1.3 / NFR-2.1 / NFR-2.2）、时序不写成因果（FR-5.9）、导出前提示（FR-5.10）。这些条款与"隐私工具"定位方向一致。

但从隐私工程角度看，**产品采集的元数据本身就是敏感数据**：完整文件路径内含用户名、文档名、项目名；域名 + 端口 + 时间戳构成目标 App 的网络行为画像；Session 元数据记录机器 OS 与权限状态。PRD 目前只覆盖了这个生命周期的一半：

- **采集 → 存储 → 展示**有定义（FR-2、FR-3、FR-4、FR-5）；
- **导出**只有一条提示（FR-5.10），无脱敏、无字段裁剪；
- **删除**完全缺失——没有任何条目规定 Session 删除、数据保留期、数据库静态保护；
- **特权采集层**（系统扩展 / ETW 服务）先看到全系统事件再过滤（NFR-1.2"内核层尽早过滤"是性能条款，不是隐私条款），其日志与崩溃转储的隐私边界未定义。

结论：**产品承诺成立，但承诺尚无对应的机制支撑**。建议在 P0 补一组"数据治理"需求（见下文 PRIV 草案），否则"隐私工具"在导出、卸载、遥测三个触点容易被用户和审核质疑。修复成本在设计期很低，在数据落盘后再补则要高一个量级。

## 隐私风险清单

| 编号 | 严重度 | 数据/场景 | 当前覆盖 | 建议 |
|------|--------|-----------|----------|------|
| PR-01 | 高 | **完整文件路径**含用户名（`/Users/<name>/`）、文档名、项目目录名、客户端代号；Session 被导出或截图分享后扩散 | FR-5.10 仅要求导出前提示"可能包含用户名、路径、域名/IP"；FR-3.2 要求记录完整 path | FR-5.10 之外补**导出脱敏选项**（用户名→`~`、文件名哈希化、路径截断到目录层）；UI 内默认展示不变，导出时用户可选 |
| PR-02 | 高 | **域名/IP + 端口 + 首末时间戳 + 流量**构成目标 App 的网络行为画像；也间接暴露用户何时在使用什么 App | FR-4.1/FR-4.2 采集定义完备；无任何保留期或删除条款 | 纳入 Session 数据治理（删除入口 + 可选保留期）；导出脱敏时对域名做可选泛化（如仅保留 eTLD+1） |
| PR-03 | 高 | **数据生命周期缺口**：Session 存 SQLite（FR-2.2）后无任何删除、保留、静态保护条款；"全本地"承诺缺少可验证的删除路径 | FR-2.2（本地存储）、FR-6.6（卸载时数据"由用户可选"，语义模糊） | 新增数据治理需求组（PRIV-1.x）：Session 删除入口、保留期选项、卸载默认行为明确化、删除可验证 |
| PR-04 | 高 | **特权采集层先见全系统事件**：ES 扩展 / ETW 服务 / ring buffer 在内核或特权进程收到全机事件，按 App 归属过滤前，非目标进程的路径与端点曾经过采集器内存、日志、崩溃转储 | NFR-1.2 的"尽早过滤"是性能目标；FR-6.4 只说"筛选后的 Session 数据"经 IPC 给 GUI | 明确为隐私条款：**非归属事件不持久化、不进日志、崩溃转储做路径脱敏或不含事件载荷**；debug 日志默认不落路径 |
| PR-05 | 中 | **敏感路径列表本身是敏感数据**：用户把哪些路径标为敏感（如某秘密项目目录、特定浏览器 profile）泄露其关注点与习惯 | FR-3.5 定义"可配置敏感路径列表"，但无存储、管理、导出条款 | 明确列表仅存本地、**默认不进导出**、提供默认集 + 用户增删；导出的敏感标记只保留命中结果不附带完整自定义列表 |
| PR-06 | 中 | **导出文件离域后失控**：JSON/CSV/MD 导出到用户自选位置后进入共享盘、聊天、issue 等不可控域 | FR-5.7（导出格式）、FR-5.10（提示） | 提示之外提供**字段裁剪**（只导 Summary 级聚合 / 排除 Timeline 明细）；导出文件头部写入"含敏感元数据"标注 |
| PR-07 | 中 | **"默认无遥测"表述留有口子**：NFR-2.2 允许"可选遥测"，但未定义遥测字段、同意门控、传输内容；隐私工具里塞遥测本身即口碑风险（企划书 §14 目标为 GitHub/HN/Reddit 传播） | NFR-2.2 一句话，无实施细则 | 收紧为：P0 **不发遥测**；若未来加入，须默认关闭、首次明确 opt-in、字段白名单且禁止含路径/域名/hostname；应用版本更新检查如联网须披露或改为用户触发 |
| PR-08 | 中 | **SQLite 明文静态存储**：Session 库含全部路径与域名，同机其他进程/用户可读；未规定文件权限与容器位置 | FR-2.2 仅说"不落盘到应用目录以外" | 规定存放于系统标准应用数据目录并设 owner-only 权限（macOS `0600` / Windows ACL）；不作强制加密，但文档化风险供 P1 评估 SQLCipher |
| PR-09 | 低 | **FileEvent 的 bytes 字段**泄露文件大小这一侧信道信息 | FR-3.2 已标 bytes 为可选 | 保留"可选"并建议 UI/导出层可整体关闭该列 |
| PR-10 | 低 | **Session 元数据与进程清单**记录 OS 版本、权限状态、executable 路径、签名身份，可推断用户环境与已装软件 | 数据模型 §6 | 纳入统一治理与导出脱敏选项即可，无需单独控制 |
| PR-11 | 低 | **崩溃恢复（FR-2.4）与 WAL/临时文件**可能在异常路径遗留事件副本 | FR-2.4 只管可恢复性 | 数据治理条款覆盖：恢复用临时文件随 Session 删除一并清理 |

## 建议新增的需求条目（PRD 格式草案）

建议新增需求组 **FR-7 数据治理与隐私控制**（或并入 NFR-2 并扩展），以下为可直接合入的草案：

### FR-7 数据治理与隐私控制（建议全部 P0，标注除外）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| FR-7.1 | 用户可在 Home / Session 列表删除单个或全部 Session；删除须物理清除对应 SQLite 记录及其聚合数据、恢复用临时文件与 WAL 残留，并在 UI 确认完成 | P0 |
| FR-7.2 | 提供可选数据保留策略（如"仅保留最近 N 个 Session"或"保留 X 天"），默认不自动删除；超限数据在启动或空闲时自动清理 | P1 |
| FR-7.3 | 应用自身的日志、崩溃报告与诊断输出不得包含文件路径、域名、IP、用户名；debug 级日志默认关闭或本地落盘前脱敏 | P0 |
| FR-7.4 | 首次运行展示本地隐私披露页：采集什么（行为元数据字段清单）、存在哪里（数据目录路径）、如何删除、应用是否联网；须持久化留档供随时查看（设置页入口） | P0 |
| FR-7.5 | 导出对话框提供脱敏选项：路径中用户名替换为 `~`；文件名可选哈希化（保留扩展名）；域名可选泛化到 eTLD+1；可仅导出 Summary 级聚合而不含事件明细 | P0 |
| FR-7.6 | 敏感路径列表仅本地存储，提供默认列表 + 用户增删改；导出的报告默认不附带完整自定义列表，只保留"命中敏感位置"的中性标记结果 | P0 |
| FR-7.7 | P0 版本不内置遥测；应用发起的任何网络请求（含版本更新检查）须在披露页列明且可由用户关闭或改为主动触发 | P0 |
| FR-7.8 | Session 数据库文件存放于系统标准应用数据目录，文件权限为 owner-only（macOS `0600`，Windows 等价 ACL）；是否加密存储作为 P1 评估项 | P0 |
| FR-7.9 | 非归属进程的事件不得持久化、不得写入日志、不得出现在崩溃转储中；ring buffer 仅驻留特权进程内存，进程退出即消失 | P0 |

### 建议补充的验收标准（并入 §9）

| 编号 | 验收项 |
|------|--------|
| AC-7 | 删除一个 Session 后，数据库、聚合结果与临时文件中不再能检索到该 Session 的任何路径或域名 |
| AC-8 | 导出脱敏模式下，导出文件中不出现本机用户名与完整文件名，且敏感路径标记结果仍可读 |
| AC-9 | 应用全量网络活动可枚举：除用户主动导出/更新检查外无任何外联（可用 ProcessLens 自身或抓包验证） |

## 需要修改的条目

| 条目 | 现状 | 建议修改 |
|------|------|----------|
| FR-5.10 | "导出前应提示报告可能包含用户名、路径、域名/IP 等敏感信息" | 升级为"提示 + 脱敏选项"：提示文案保留，同时按 FR-7.5 提供用户名掩码、文件名哈希、仅聚合导出等选项；仅提示不防护，等于把责任全部转嫁给用户 |
| FR-6.6 | "移除系统扩展 / 服务与本地数据由用户可选" | 语义收紧：卸载流程中**明确询问**是否删除本地 Session 数据（默认勾选删除或明确不删），删除范围覆盖数据库、日志、敏感路径配置；当前"可选"未规定交互与默认值 |
| NFR-1.2 | "事件在内核层尽早过滤"（纯性能表述） | 补一句隐私语义：非归属事件过滤后不持久化、不进日志（与 FR-7.9 呼应），把"尽早过滤"同时定义为隐私边界 |
| NFR-2.2 | "可选遥测必须完全独立且默认关闭" | 改为"P0 不内置遥测；任何应用发起的网络请求须披露并可关闭"（与 FR-7.7 对齐）。隐私工具保留遥测口子，是 GitHub/HN 受众最容易攻击的点 |
| 术语表 §2 | Sensitive Location 定义止于"仅作中性标记" | 补充其数据属性："列表本身仅本地存储，默认不随报告导出"，避免该列表被当作普通配置随手导出 |
| 数据模型 §6 | 各对象字段表 | 建议增加一列"敏感性/脱敏规则"（如 path→含用户名与文件名；hostname→画像要素；bytes→可选侧信道），让数据模型自带数据地图，成为后续实现与审计的基准 |
| 企划书 §13（上游） | "导出前提示可能包含用户名、路径、域名/IP 等敏感信息" | 上游同样建议把"提示"升级为"提示 + 可选脱敏"，保持企划与 PRD 一致 |

### 与"隐私工具"定位一致性说明

未发现与定位直接冲突的条款。两个容易被质疑的表述：

1. **NFR-2.2 的"可选遥测"**：在"默认无遥测"的免费隐私工具里预留遥测入口，即使默认关闭也会被社区视为信用减分项；建议 P0 直接不做。
2. **FR-6.6 的"本地数据由用户可选"**：措辞模糊，审核者会问"默认删不删、删得干不干净"；按上表收紧即可。

另需提示一个**定位层面的固有限制**（非缺陷）：产品可见"目标 App 读了哪些文件"与"连了哪些地址"，但无法证明文件内容被上传（FR-5.9 已正确处理时序≠因果）。同理，本工具展示的是**被监控 App 的行为**，而 ProcessLens 自身采集的元数据同样需要治理——这正是 FR-7 组存在的理由：隐私工具自身的数据卫生必须经得起它要求别人接受的审视。
